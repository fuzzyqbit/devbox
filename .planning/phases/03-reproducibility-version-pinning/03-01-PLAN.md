<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Galaxy registry → bake host | Untrusted upstream; pinned versions are the only mitigation against malicious release replacement |
| Terraform Registry → operator/CI | Untrusted upstream; provider lockfile checksums are the trust anchor |
| Git → all downstream consumers | The repo's `requirements.yml` and `.terraform.lock.hcl` are the source of truth — corruption here cascades to every bake |
| Vendored CIS role's git source repos (github.com/ansible-collections/*) → bake host | Untrusted upstream; pinned tag refs are the only mitigation |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Tampering | hashicorp/aws provider binary | mitigate | `.terraform.lock.hcl` records SHA256 (h1:) hashes for all 4 platforms; `tofu init -lockfile=readonly` (Phase 4 CI per 03-RESEARCH.md:695) refuses to run if the downloaded binary doesn't match |
| T-03-02 | Tampering | Galaxy collection tarball replacement | mitigate | `==X.Y.Z` (exact equality) in `ansible/requirements.yml`; Galaxy server enforces version immutability — a republished version with the same number would not resolve against the pinned record. Defense in depth: Phase 4 CI will run `ansible-galaxy collection install --offline` against a pre-populated cache (per 03-RESEARCH.md:696) |
| T-03-03 | Tampering | CIS-role vendored git-source collection ref poisoning | mitigate | `version: X.Y.Z` resolves to a git TAG. Tags can be force-pushed on most providers, but the ansible-collections org has tag-protection rules. Residual risk accepted given personal-devbox threat surface; upgrade to commit SHA pinning if a higher bar is needed (note in SUMMARY for follow-up) |
| T-03-04 | Repudiation | "Who bumped this version?" | mitigate | Every pin change is a reviewable git diff in `requirements.yml` or `.terraform.lock.hcl`; git log + blame on the specific line is the audit trail |
| T-03-05 | Information Disclosure | Lockfile contains version metadata | accept | Lockfile contents are public information (provider versions + public hashes); no secrets leak |
| T-03-06 | Denial of Service | Upstream Galaxy/Registry takedown of a pinned version | accept | If a Galaxy collection version is yanked AND no cached copy exists, bake fails. Probability low (PEP 440 pins are not auto-yanked); recovery: bump to next-available version + commit (Pitfall 2 at 03-RESEARCH.md:398-407). Defense in depth: Phase 4 CI populates a runner-level cache |
| T-03-07 | Elevation of Privilege | Bake-time code in pinned collection runs as root on the bake instance | mitigate | Pinning to a reviewed tagged release (not floating HEAD) means the executor reviewed THIS specific tarball — not any future master-branch state. Defense in depth: bake host is ephemeral (Packer EBS-backed, destroyed after bake), so a single compromised bake does not persist |

**Note on T-03-03 (git tag mutability):** The decision to use tagged refs instead of immutable commit SHAs in the vendored CIS role's `collections/requirements.yml` matches Pattern 3 at 03-RESEARCH.md:227-254 — tags are human-readable and stay in lockstep with the top-level `requirements.yml`. The trade-off is documented; bumping to SHA pinning is a noted follow-up.
