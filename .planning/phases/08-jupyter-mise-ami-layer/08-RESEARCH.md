## Summary

Phase 8 adds two independent concerns to the existing Ansible playbook: a JupyterLab service and the mise version manager. Both fit cleanly into the established role model. JupyterLab follows the code-server pattern exactly (install binary/package → write config → install+enable systemd unit) with one material difference: JupyterLab needs a **hashed** password at runtime, not cleartext, requiring the boot oneshot to generate the hash from the SSM-fetched cleartext.

The two most important technical details a planner must get right: (1) the correct config key for modern jupyter-server 2.x is `c.PasswordIdentityProvider.hashed_password` (not the deprecated `c.ServerApp.password`), and the Python one-liner to generate the hash non-interactively from the venv is `python3 -c "from jupyter_server.auth import passwd; print(passwd('CLEARTEXT'))"`. (2) mise activation via `/etc/profile.d` requires a file that calls `eval "$(mise activate bash)"` — the official docs recommend per-user `~/.bashrc`, but `/etc/profile.d/mise.sh` is the correct system-wide mechanism and is supported by AL2023's `/etc/profile` sourcing all `*.sh` files in that directory.

A **critical pitfall** requires explicit attention: argon2-cffi vendors its own C implementation (not OpenSSL), so FIPS mode enforced at the OpenSSL level does not block argon2 hashing. However, this should be flagged as an open question for the operator since it is `[ASSUMED]` based on argon2-cffi's documentation stating it vendors Argon2 C code by default, and no direct AL2023 FIPS + argon2-cffi test was run in this session.

**Primary recommendation:** Two new Ansible roles (`jupyter`, `mise`) following the vscode/certs role shape respectively; `secrets` role extended for the Jupyter password; boot oneshot template extended to fetch + hash + write Jupyter config and add `jupyter.service` to the restart loop.

### Pattern 1: systemd unit for JupyterLab (mirrors code-server.service.j2)

**What:** Type=simple, User/Group=ec2-user, ExecStart uses venv python directly, no `--bind-addr` flag — Jupyter uses `--ip` and `--port` separately.

**When to use:** Any browser-facing service running as ec2-user.

```ini
# Source: modeled on ansible/roles/vscode/templates/code-server.service.j2
# and https://janakiev.com/blog/jupyter-systemd/
[Unit]
Description=JupyterLab
After=network.target

[Service]
Type=simple
User={{ dev_user }}
Group={{ dev_user }}
ExecStart={{ jupyter_venv_path }}/bin/jupyter lab \
    --ip={{ jupyter_bind_ip }} \
    --port={{ jupyter_port }} \
    --no-browser \
    --certfile={{ jupyter_cert_dir }}/jupyter-cert.pem \
    --keyfile={{ jupyter_cert_dir }}/jupyter-key.pem \
    --notebook-dir={{ dev_home }}
Restart=on-failure
RestartSec=5
Environment=HOME={{ dev_home }}

[Install]
WantedBy=multi-user.target
```

**Key difference from code-server:** code-server reads its config file (`~/.config/code-server/config.yaml`); JupyterLab reads `~/.jupyter/jupyter_server_config.py`. The `--certfile`/`--keyfile` must be CLI flags or config keys — `cert: true` is a code-server-ism, not a Jupyter concept.

### Pattern 2: Password hash generation at boot

**What:** Non-interactive one-liner using the venv's Python to call `passwd()` with the cleartext.

**When to use:** Boot oneshot only. Never at bake time (cleartext must not land in AMI).

```bash
# Source: jupyter-server.readthedocs.io/en/latest/operators/public-server.html
# Pattern: call passwd() with the cleartext argument directly
HASH=$(/opt/jupyter/bin/python3 -c \
    "from jupyter_server.auth import passwd; print(passwd('${JUPYTER_PWD}'))")

# Write config (config key for jupyter-server 2.x)
install -d -o ec2-user -g ec2-user -m 0700 /home/ec2-user/.jupyter
cat > /home/ec2-user/.jupyter/jupyter_server_config.py <<EOF
c.PasswordIdentityProvider.hashed_password = '${HASH}'
EOF
chown ec2-user:ec2-user /home/ec2-user/.jupyter/jupyter_server_config.py
chmod 0600 /home/ec2-user/.jupyter/jupyter_server_config.py
```

**Config precedence note:** `jupyter_server_config.json` takes precedence over `jupyter_server_config.py`. The boot script must write the `.py` file only; never create a `.json` file, or the `.py` password will be silently ignored if a `.json` also exists. [CITED: jupyter-server.readthedocs.io]

### Pattern 3: Jupyter TLS cert generation (mirrors noVNC pattern)

```yaml
# Source: modeled on ansible/roles/desktop/tasks/main.yml lines 152-175
- name: Create Jupyter TLS cert directory
  file:
    path: "{{ jupyter_cert_dir }}"   # e.g. /etc/jupyter
    state: directory
    mode: "0755"

- name: Generate self-signed TLS cert for Jupyter
  command: >
    openssl req -x509 -nodes -newkey rsa:2048
    -keyout {{ jupyter_cert_dir }}/jupyter-key.pem
    -out {{ jupyter_cert_dir }}/jupyter-cert.pem
    -days 3650 -subj '/CN=devbox'
  args:
    creates: "{{ jupyter_cert_dir }}/jupyter-cert.pem"

- name: Set Jupyter cert/key permissions
  file:
    path: "{{ item.path }}"
    owner: root
    group: "{{ dev_user }}"
    mode: "{{ item.mode }}"
  loop:
    - { path: "{{ jupyter_cert_dir }}/jupyter-cert.pem", mode: "0644" }
    - { path: "{{ jupyter_cert_dir }}/jupyter-key.pem",  mode: "0640" }
```

### Pattern 4: mise binary install + profile.d activation

```yaml
# Source: mise.jdx.dev/installing-mise.html + certs role profile.d pattern
- name: Download mise binary
  get_url:
    url: "https://github.com/jdx/mise/releases/download/v{{ mise_version }}/mise-v{{ mise_version }}-linux-x64"
    dest: "{{ mise_install_dir }}/mise"
    mode: "0755"
    checksum: "sha256:{{ mise_checksum_sha256 }}"

- name: Write mise system-wide bash activation
  copy:
    dest: /etc/profile.d/mise.sh
    mode: "0644"
    content: |
      # mise version manager — system-wide bash activation (Phase 8 MISE-02)
      eval "$(mise activate bash)"
```

**The checksum value** must be looked up from `https://github.com/jdx/mise/releases/download/v{{ mise_version }}/SHASUMS256.txt` and recorded in `defaults/main.yml` as `mise_checksum_sha256`. The `get_url` module's `checksum:` key accepts `sha256:<hex>` format directly.

**Why profile.d works:** AL2023's `/etc/profile` sources all `*.sh` files from `/etc/profile.d/`. This is the same mechanism used by the existing `certs` role (`/etc/profile.d/ca-trust.sh`). [VERIFIED: ansible/roles/certs/tasks/main.yml line 23-26]

### Pattern 5: ipykernel registration

```bash
# After pip install ipykernel into the venv:
/opt/jupyter/bin/python3 -m ipykernel install \
    --prefix /opt/jupyter \
    --name python3 \
    --display-name "Python 3"
```

Using `--prefix /opt/jupyter` (not `--user`) installs the kernelspec into the venv's share directory, making it discoverable when Jupyter runs from that venv. `--user` would install into `~/.local` which is not available at bake time for ec2-user under root's Ansible context. [CITED: ipython.readthedocs.io/en/stable/install/kernel_install.html]

### Anti-Patterns to Avoid

- **Baking the cleartext password into any config file at bake time.** The `jupyter_server_config.py` written by the `jupyter` role at bake time must contain a placeholder comment only, OR the file must not exist at bake time at all (the boot oneshot creates it). Never set `c.PasswordIdentityProvider.hashed_password` during the Packer build.
- **Using `c.ServerApp.password` instead of `c.PasswordIdentityProvider.hashed_password`.** The old key is deprecated in jupyter-server 2.x; it may still work as a compatibility shim but the correct key must be used for correctness and forward-compatibility. [CITED: docs]
- **Using `--user` flag with ipykernel install inside a root-context Ansible task.** `--user` installs into root's `~/.local`, not the venv, making the kernel invisible to ec2-user's Jupyter service.
- **Putting `mise activate` in `~/.bashrc` instead of `/etc/profile.d/mise.sh`.** SSM sessions start a login shell; `/etc/profile.d/` is sourced for login shells. `~/.bashrc` alone is not sourced for login shells — it requires `.bash_profile` to source it. System-wide profile.d is the correct target.
- **Floating `latest` in the mise download URL.** The project's grep-gate at pre-commit (gate #3 checks for `<RESOLVED-VERSION>` placeholders; gate #1 checks `most_recent`) and the CI `grep-gates` job enforce explicit version pins. The mise role's `defaults/main.yml` must declare `mise_version: "2026.5.18"` (quoted string, following convention).
- **Creating `jupyter_server_config.json` in addition to `.py`.** The JSON file takes precedence over Python; if both exist, the Python file's password is silently ignored.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Password hashing | Custom hash routine in bash | `from jupyter_server.auth import passwd; passwd(cleartext)` inside venv Python | Argon2id with correct parameters; correct format string; matches what Jupyter's verifier expects |
| Kernel registration | Manual kernelspec JSON | `python -m ipykernel install --prefix /opt/jupyter` | Generates correct kernelspec at the path Jupyter searches |
| Venv Python activation in systemd | `source /opt/jupyter/bin/activate` in ExecStart | Use absolute path to venv binary: `/opt/jupyter/bin/jupyter` | systemd units cannot `source`; absolute venv path is the correct pattern |
| mise install from source | Compile from Rust source | Direct binary download from GitHub Releases | Official binary; checksum verifiable; compile adds no security value and ~10 min to bake time |
| Self-signed cert generation | Copying code-server's cert files | `openssl req -x509` at bake time under `/etc/jupyter/` | code-server manages its own cert lifecycle; sharing creates coupling between two independent services |

**Key insight:** The venv binary path trick (calling `/opt/jupyter/bin/jupyter` directly rather than activating the venv) is the standard pattern for systemd services. The venv's `bin/jupyter` launcher already has the correct shebang pointing to the venv Python.

## Common Pitfalls

### Pitfall 1: Wrong password config key (most likely mistake)

**What goes wrong:** Password appears set but Jupyter starts without authentication — or worse, with no visible error.
**Why it happens:** `c.ServerApp.password` was the correct key in jupyter-server 1.x / JupyterLab 3.x. In jupyter-server 2.x (which backs JupyterLab 4.x), authentication is delegated to `PasswordIdentityProvider`. The old key may be silently ignored or may work as a deprecated alias in some versions but break on upgrade.
**How to avoid:** Always use `c.PasswordIdentityProvider.hashed_password` in `jupyter_server_config.py`. [CITED: jupyter-server.readthedocs.io — "ServerApp.password is deprecated in 2.0; use PasswordIdentityProvider.hashed_password"]
**Warning signs:** JupyterLab starts and is reachable without entering any password.

### Pitfall 2: ipykernel installed to wrong location

**What goes wrong:** JupyterLab starts but shows "No kernel" or an empty kernel list.
**Why it happens:** `python -m ipykernel install --user` (without `--prefix`) installs the kernelspec into root's `~/.local/share/jupyter/kernels/` during the Packer Ansible run (which runs as root). The service runs as ec2-user, which looks in `/opt/jupyter/share/jupyter/kernels/` and `~ec2-user/.local/`.
**How to avoid:** Always use `--prefix /opt/jupyter` so the kernelspec lands in `/opt/jupyter/share/jupyter/kernels/python3/`.
**Warning signs:** `jupyter kernelspec list` run as ec2-user shows empty or only default paths outside the venv.

### Pitfall 3: `c.PasswordIdentityProvider.hashed_password` silently overridden by `.json`

**What goes wrong:** Boot oneshot writes the hashed password to `jupyter_server_config.py`, but if any process has created `jupyter_server_config.json` (e.g. running `jupyter server password` interactively), the JSON takes precedence and the Python config is ignored.
**Why it happens:** Jupyter's config precedence rule: `.json` > `.py`. [CITED: jupyter-server.readthedocs.io]
**How to avoid:** The boot script and role must never create or allow creation of `jupyter_server_config.json`. Document this in role comments.
**Warning signs:** Password is wrong; `jupyter_server_config.json` file exists in `~/.jupyter/`.

### Pitfall 4: Hardening runs AFTER jupyter role but BEFORE restart

**What goes wrong:** The `hardening` role reboots the system (SELinux enforcing, FIPS). If `jupyter.service` is enabled and starts before reboot completes, the first-boot sequence races with the reboot. More critically: `devbox-secrets-bootstrap.service` must complete before `jupyter.service` starts.
**Why it happens:** The systemd unit ordering needs `Before=jupyter.service` in the bootstrap unit, which already exists in the template; and `After=devbox-secrets-bootstrap.service` in the jupyter unit.
**How to avoid:** Add `After=devbox-secrets-bootstrap.service` to the `[Unit]` section of `jupyter.service.j2`; add `jupyter.service` to the `Before=` line in `devbox-secrets-bootstrap.service.j2`.
**Warning signs:** Jupyter starts before password is written; error in journal: "No hashed_password configured".

### Pitfall 5: FIPS mode and argon2 (flag for operator)

**What goes wrong:** argon2-cffi's hash generation fails at runtime on the FIPS-enabled AL2023 instance, blocking the boot oneshot.
**Why it is likely safe:** argon2-cffi vendors its own Argon2 C implementation and does not call OpenSSL. FIPS mode restrictions apply to OpenSSL-backed operations; argon2-cffi bypasses OpenSSL entirely. [CITED: argon2-cffi.readthedocs.io/en/stable/installation.html — "vendors Argon2's C code by default"]
**Why it is not fully verified:** No direct test of argon2-cffi on an AL2023 FIPS instance was run in this research session. This is `[ASSUMED]` from documentation.
**Mitigation if it fails:** `jupyter_server.auth.passwd(cleartext, algorithm='sha256')` produces a hashlib-based hash (`sha256:<salt>:<hex>`) which is FIPS-compliant (SHA-256 is FIPS-approved). The `c.PasswordIdentityProvider.hashed_password` key accepts this format. The boot script can detect failure and fall back: `HASH=$(.../python3 -c "..." 2>/dev/null) || HASH=$(.../python3 -c "...algorithm='sha256'...")`.
**Warning signs:** Boot oneshot fails with `argon2.exceptions.HashingError` in `journalctl -u devbox-secrets-bootstrap`.

### Pitfall 6: mise activation in non-login SSM sessions

**What goes wrong:** `mise` is not on PATH in SSM sessions because `eval "$(mise activate bash)"` in `/etc/profile.d/mise.sh` only fires in login shells.
**Why it happens:** SSM Session Manager by default starts a non-login, non-interactive bash shell. `/etc/profile.d/` scripts are only sourced for login shells.
**How to avoid:** This is acceptable for the current scope (MISE-02 says "interactive shells"). Document that users must start a login shell: `bash -l` or `exec bash --login`. The AWS SSM shell type can be configured in Session Manager preferences to use `bash -l`.
**Warning signs:** `mise --version` fails in an SSM session; works fine in a local `bash -l`.

### Pitfall 7: Version floating via `latest` URL redirect

**What goes wrong:** Pre-commit grep-gate gate #3 (`! grep -r -- "<RESOLVED-VERSION>" packer/`) does not catch this, but the spirit of the reproducibility invariant is violated. `get_url` with a `latest`-redirecting URL produces a non-pinned, non-reproducible build.
**Why it happens:** mise's install page shows `curl https://mise.run | sh` — this always pulls latest.
**How to avoid:** Use the explicit GitHub Releases URL with the pinned version in `defaults/main.yml`: `mise_version: "2026.5.18"`. Fetch the checksum from `SHASUMS256.txt` and pin `mise_checksum_sha256` in defaults too. [VERIFIED: github.com/jdx/mise/releases — SHASUMS256.txt exists]

### Full boot oneshot extension (diff-style, bash)

```bash
# [ASSUMED] — exact bash structure follows devbox-secrets-bootstrap.sh.j2 pattern
# Fetch Jupyter password from SSM (add after existing CS_PWD/VNC_PWD fetches)
JUPYTER_PWD=$(aws ssm get-parameter --region "$REGION" \
    --name "/devbox/$DEVBOX_USER/jupyter-password" \
    --with-decryption --query 'Parameter.Value' --output text)

if [[ -z "$JUPYTER_PWD" ]]; then
    echo "Empty jupyter-password from SSM; refusing to write empty config" >&2
    exit 1
fi

# Hash password using venv Python (argon2 by default; FIPS fallback on error)
JUPYTER_HASH=$(/opt/jupyter/bin/python3 -c \
    "from jupyter_server.auth import passwd; print(passwd('${JUPYTER_PWD}'))" 2>/dev/null) \
    || JUPYTER_HASH=$(/opt/jupyter/bin/python3 -c \
    "from jupyter_server.auth import passwd; print(passwd('${JUPYTER_PWD}', algorithm='sha256'))")

if [[ -z "$JUPYTER_HASH" ]]; then
    echo "Failed to hash jupyter password; refusing to write empty config" >&2
    exit 1
fi

# Write Jupyter config (jupyter-server 2.x key)
install -d -o ec2-user -g ec2-user -m 0700 /home/ec2-user/.jupyter
cat > /home/ec2-user/.jupyter/jupyter_server_config.py <<EOF
# Written by devbox-secrets-bootstrap at boot. Do not edit manually.
c.PasswordIdentityProvider.hashed_password = '${JUPYTER_HASH}'
EOF
chown ec2-user:ec2-user /home/ec2-user/.jupyter/jupyter_server_config.py
chmod 0600 /home/ec2-user/.jupyter/jupyter_server_config.py

# Add jupyter.service to the restart loop (existing loop already handles missing units)
```

## Open Questions

1. **FIPS + argon2 runtime behavior (A1)**
   - What we know: argon2-cffi vendors its own C code; FIPS mode restricts OpenSSL-backed operations; the boot script can fall back to `algorithm='sha256'`
   - What's unclear: Whether AL2023's Python FIPS hooks (Python 3.9+ honors `usedforsecurity=False`) affect cffi-invoked C code at all
   - Recommendation: Include the argon2 → sha256 fallback in the boot script unconditionally; it costs nothing and handles both FIPS and non-FIPS environments

2. **mise SHA-256 checksum for v2026.5.18 linux-x64 (A5)**
   - What we know: `SHASUMS256.txt` exists at the release URL (HTTP 302 confirmed)
   - What's unclear: The planner must fetch the actual hex value from `SHASUMS256.txt` and hard-code it into `defaults/main.yml`
   - Recommendation: Wave 0 task — `curl -L https://github.com/jdx/mise/releases/download/v2026.5.18/SHASUMS256.txt | grep linux-x64$` and record in defaults

3. **`c.PasswordIdentityProvider.hashed_password` vs `c.ServerApp.password` in jupyter-server 2.19.0**
   - What we know: Search result states "ServerApp.password is deprecated in 2.0; use PasswordIdentityProvider.hashed_password instead" [CITED: search result cross-referencing jupyter-server docs]
   - What's unclear: Whether the old key still works as an alias in 2.19.0 for resilience
   - Recommendation: Use the new key; add a comment in the boot script noting the deprecation

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | `c.PasswordIdentityProvider.hashed_password` (argon2id); password sourced from SSM SecureString |
| V3 Session Management | partial | Jupyter uses its own token/cookie mechanism; HTTPS enforced via TLS cert |
| V4 Access Control | no | Single-user instance; no multi-tenant concerns |
| V5 Input Validation | no | No user-provided input processed by Ansible |
| V6 Cryptography | yes | Self-signed cert (RSA-2048); argon2id password hash; FIPS fallback to SHA-256 HMAC |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Jupyter running without password (tokenless) | Information Disclosure | `c.PasswordIdentityProvider.hashed_password` + `c.ServerApp.open_browser = False`; no token auth path |
| Password cleartext in AMI snapshot | Disclosure | Boot-time injection via SSM SecureString; cleartext never written to disk at bake time |
| Self-signed cert bypass (MITM) | Spoofing | Acceptable per project posture (same as code-server/noVNC); SG restricts access to `var.allowed_web_cidrs` |
| Open `/etc/jupyter/*.pem` key | Disclosure | Key file permissions `0640` root:ec2-user (mirrors noVNC pattern) |
| mise `eval` execution in login shell | Tampering | Binary checksum-pinned via `get_url checksum:`; binary from official GitHub Releases |
