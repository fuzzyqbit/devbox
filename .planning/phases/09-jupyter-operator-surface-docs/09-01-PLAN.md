Access model (LOCKED, from Phase 8 loopback pivot):
- JupyterLab is NOT a systemd service. It is launched on demand by `./run jupyter`,
  which runs `jupyter lab --ip=127.0.0.1 --port=8888 --no-browser` over an SSM
  interactive session and prints a `http://127.0.0.1:8888/lab?token=...` URL.
- To reach it the operator opens a SECOND shell and runs an SSM port-forward:
    aws ssm start-session --target <id> --region <region> \
      --document-name AWS-StartPortForwardingSession \
      --parameters '{"portNumber":["8888"],"localPortNumber":["8888"]}'
  then opens the printed `http://127.0.0.1:8888/lab?token=...` URL.
- There is NO password and NO TLS. Loopback + SSM/IAM is the auth boundary.
- `./run devbox-port-forward` stays code-server-only; there is NO dedicated
  `./run jupyter-port-forward` command (operator forwards :8888 manually).

scripts/devbox-status.sh — current Connection Info block (only prints when
$STATE == "running"), lines ~46-63. Existing lines use $INSTANCE_ID, $REGION,
$PRIVATE_IP, $DEVBOX_USER. The code-server line is:
  echo "code-server (browser): https://${PRIVATE_IP}:8080  (reachable from VPC; ...)"
The new Jupyter line must NOT imply a network-reachable https://<ip>:8888 URL —
it is loopback-only and on demand.

docs/DEVELOPER-LIFECYCLE.md — relevant anchors:
- "### Browser IDE (code-server on :8080)" subsection ends ~line 93 (before "### Passwords").
- Cheat-sheet table header at line 125; rows lines 126-136.
