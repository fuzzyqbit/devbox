# Phase 01 Plan 02: SSM Distribution + IAM Instance Profile + Per-operator SSH Key

Closes SEC-03 and SEC-04. The per-build secrets generated by 01-PLAN's `secrets` role now travel from the Packer bake host → AWS SSM Parameter Store (SecureString) → the running EC2's instance profile → the boot-time systemd oneshot → `~/.config/code-server/config.yaml` and `~/.vnc/passwd`. No static AWS credentials are baked into the AMI; no secret material lives in user_data, tfstate, or the Git repo. Operators retrieve the per-user values via `make secrets-show DEVBOX_USER=$USER`, and authorize themselves via per-operator SSH keys (`${local.user}-devbox`) imported out-of-band.

## Final shape of the `secrets` role

`ansible/roles/secrets/tasks/main.yml` is now the three-step gate:

```yaml
---
- name: Generate per-build secrets
  ansible.builtin.import_tasks: generate.yml

- name: Publish per-build secrets to AWS SSM Parameter Store
  ansible.builtin.import_tasks: publish.yml

- name: Install boot-time secret bootstrap (systemd oneshot)
  ansible.builtin.import_tasks: install-oneshot.yml
```

Ordering enforcement: `generate` binds the facts → `publish` writes to SSM → `install-oneshot` bakes the bootstrap unit + script into the AMI. SSM is guaranteed populated by the time the AMI ships.

## IAM policy JSON as written into `terraform/main.tf`

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadOwnSecrets",
      "Effect": "Allow",
      "Action": [
        "ssm:GetParameter",
        "ssm:GetParameters",
        "ssm:GetParametersByPath"
      ],
      "Resource": "arn:aws:ssm:${data.aws_region.current.region}:${data.aws_caller_identity.current.account_id}:parameter/devbox/${var.devbox_user}/*"
    },
    {
      "Sid": "DecryptSecureStrings",
      "Effect": "Allow",
      "Action": ["kms:Decrypt"],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "kms:ViaService": "ssm.${data.aws_region.current.region}.amazonaws.com"
        }
      }
    }
  ]
}
```

Two least-privilege guarantees:

1. **Resource scoping** — the EC2 can only read SSM parameters whose names start with `/devbox/<its own DevboxUser>/`. It cannot read another user's parameters even if it learns the path.
2. **kms:ViaService condition** — the `kms:Decrypt` is only allowed when the request is brokered by SSM (`kms:ViaService = ssm.<region>.amazonaws.com`). The EC2 cannot directly call KMS, and cannot decrypt SecureStrings belonging to other users or other AWS services that happen to share the `alias/aws/ssm` key.

The role is bound to `aws_instance.devbox` via `iam_instance_profile = aws_iam_instance_profile.devbox.name` (line 147 of `terraform/main.tf`). The metadata_options block on the same resource enforces IMDSv2 (`http_tokens = "required"`), exposes the `DevboxUser` tag via instance metadata (`instance_metadata_tags = "enabled"`), and caps the IMDS hop limit at 1 (containers cannot reach IMDS).

## Bootstrap script's IMDSv2-token + tag-metadata flow

The systemd oneshot service `devbox-secrets-bootstrap.service` runs at first boot, before `code-server.service`, `vncserver.service`, and `novnc.service`. Its `ExecStart` calls `/usr/local/sbin/devbox-secrets-bootstrap.sh`, which walks the following path:

1. **IMDSv2 session token** — `curl -fsS -X PUT http://169.254.169.254/latest/api/token -H 'X-aws-ec2-metadata-token-ttl-seconds: 60'`. Required because the instance enforces `http_tokens=required`; IMDSv1 calls are rejected at the metadata service layer.
2. **Region + DevboxUser via tag-in-metadata** — `curl -fsS -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/placement/region` and `.../meta-data/tags/instance/DevboxUser`. The `DevboxUser` tag is set on the EC2 by `aws_instance.devbox` (line 161 of `terraform/main.tf`); exposing it via tag-in-metadata means the bootstrap needs zero `ec2:DescribeTags` API permission (smaller IAM surface, per RESEARCH.md Open Question 2).
3. **SSM SecureString fetch** — `aws ssm get-parameter --region "$REGION" --name "/devbox/$DEVBOX_USER/code-server-password" --with-decryption --query 'Parameter.Value' --output text` (and the analogous `/vnc-password`). AWS CLI v2 (installed by `ansible/roles/base/tasks/main.yml`) transparently uses the instance profile credentials.
4. **Config write** — `~/.config/code-server/config.yaml` is rewritten in place (0600, owned ec2-user). The VNC password is piped via `printf '%s' "$VNC_PWD" | sudo -u ec2-user vncpasswd -f > ~/.vnc/passwd` — `printf '%s'` (not `echo`) avoids the trailing newline that VNC would treat as part of the password.
5. **Mark complete** — `touch /var/lib/devbox/secrets-applied`. This is the `ConditionPathExists=!` guard the systemd unit honors; the oneshot will not re-fire on reboot, but a new instance launched from the same AMI starts without the marker and re-fetches.
6. **Restart dependents** — `for svc in code-server.service vncserver.service novnc.service; do if systemctl list-unit-files "$svc"; then systemctl restart "$svc"; fi; done`. Tolerates missing optional units (a vscode-only build with no desktop layer still works).

The script uses `set -euo pipefail` and `curl -fsS`; any IMDS / SSM / KMS failure causes a non-zero exit. systemd then marks the unit failed, and because dependent units have `After=devbox-secrets-bootstrap.service` implied by `Before=` ordering, code-server/vncserver/novnc never start with stale config.

## Breaking Changes & Operator Migration Steps

### 1. `key_name = "me"` -> `key_name = "${local.user}-devbox"`

Existing operators whose AWS keypair is named `"me"` will fail `make tg-apply` after this plan merges. Two remediation paths:

**Option A (recommended) — Re-import under the per-operator name:**
```bash
# Generate a fresh ed25519 key if you don't already have one:
ssh-keygen -t ed25519 -f "$HOME/.ssh/${USER}-devbox" -C "${USER}@devbox-$(date +%Y%m%d)"

# Import the public key into AWS under the new naming scheme:
aws ec2 import-key-pair \
    --key-name "${USER}-devbox" \
    --public-key-material "fileb://$HOME/.ssh/${USER}-devbox.pub" \
    --region "$AWS_REGION"

# Confirm:
aws ec2 describe-key-pairs --key-names "${USER}-devbox" --region "$AWS_REGION"

# Then:
make tg-apply DEVBOX_USER="$USER"
```

**Option B (transitional, if a running devbox can't be replaced yet) — keep the legacy key name:**
```bash
# Re-import the same public key under both names:
aws ec2 import-key-pair --key-name "me-devbox" \
    --public-key-material "fileb://$HOME/.ssh/me-devbox.pub" \
    --region "$AWS_REGION"
# Then `export DEVBOX_USER=me` so `local.user = "me"` -> key_name resolves to "me-devbox".
```

**Rotation** (one-shot per operator per rotation event): `aws ec2 delete-key-pair --key-name "${USER}-devbox" && aws ec2 import-key-pair --key-name "${USER}-devbox" --public-key-material fileb:// ...`. The running EC2 must be replaced (`terraform destroy && terraform apply`) because AWS does not push a new public key to a running instance.

### 2. `var.iam_instance_profile` removed from the Terraform module's public interface

Operators who set `iam_instance_profile = "..."` in their Terragrunt inputs would now hit `Error: Unsupported argument`. **Verified safe for this repo**: `terragrunt.hcl` never set it (default was `null`). Documented in commit `187d57d`. Multi-tenant consumers (none today, per PROJECT.md "Multi-tenant / shared infrastructure: out of scope") would need to drop the input.

### 3. Pre-Phase-1 baked AMIs continue to ship `changeme`

The systemd oneshot baked by `install-oneshot.yml` only exists in AMIs baked AFTER this plan merges. An operator running an old AMI must:
1. `make build` to bake a new AMI (writes the new SSM params, bakes the bootstrap into the AMI).
2. Update `terragrunt.hcl:30` (`ami_id`) to the new AMI ID.
3. `make tg-apply` to replace the instance (which will fetch from SSM on first boot).

Phase 3 (REP-05) automates the AMI-ID handoff.
