<objective>
Install repository-level secret-scanning gates that catch any new `changeme`-class regression OR any committed AWS / GitHub / Slack / etc. secret BEFORE it reaches the remote. Two gates, one config:

1. **Pre-commit (developer-machine):** `.pre-commit-config.yaml` runs `gitleaks v8.30.1` and a local `no-changeme` guard on every `git commit`.
2. **CI (server-side):** `.github/workflows/security.yml` runs `gitleaks-action@v2` on every push and PR. This is the LAST line of defense — even a `--no-verify` bypass on the developer side is caught.

- It does NOT add `terraform fmt -check`, `ansible-lint`, `shellcheck`, `tfsec`, or any other CI checks — Phase 4 (CI-01..CI-07) owns those and will extend the same two files.

This is the only way to verify CI is wired correctly without merging the workflow to `main` first.

```toml
# gitleaks configuration — extends the default ruleset with project-specific allowances.
# See: https://github.com/gitleaks/gitleaks#configuration

# Extend the upstream default rules; this file ADDS allowances, does not replace.
[extend]
useDefault = true

[allowlist]
description = "Permit canonical example keys in documentation and planning artifacts"
paths = [
  '''\.planning/.*''',
  '''.*\.md''',
]
regexes = [
  # The canonical AWS docs example. RESEARCH.md and SUMMARY.md need to reference it.
  '''AKIAIOSFODNN7EXAMPLE''',
  # The canonical AWS docs example secret key.
  '''wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY''',
]
```

Notes:
- `[extend].useDefault = true` is the documented way to keep ALL upstream rules (200+ patterns) while adding overrides — see gitleaks docs.
- The two regex allowances are the AWS-documented example credentials. They are intentionally well-known and pose no security risk; only allowed inside `.planning/**` or `*.md`.
- DO NOT add allowances for `changeme` here — that gate is enforced by the local pre-commit hook (Task 1), which is intentionally NOT enforced by gitleaks (different layer).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Developer working tree → git index → local repo | Pre-commit hook runs at the index→repo boundary. Failure aborts the commit before it lands in `.git/objects`. |
| Local repo → remote (origin) | CI workflow runs after the push reaches origin. Detected secrets fail the workflow, which (for PRs) blocks merge via branch protection (operator action, not in repo). |
| Action consumer → action publisher | GitHub Actions execute third-party code. SHA-pinning (vs tag-pinning) prevents a malicious publisher from retroactively poisoning a previously-trusted release. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Information Disclosure | Secret committed and pushed to public origin | mitigate | Two gates: pre-commit (developer-side, default) + CI (server-side, can't be bypassed). gitleaks v8.30.1's default ruleset covers AWS, GCP, GitHub, Slack, Stripe, npm, JWT, RSA private keys, etc. (200+ rules). |
| T-03-02 | Spoofing | Operator passes `git commit --no-verify` to bypass the local hook | mitigate (at CI layer) | The push reaches origin and triggers `security.yml`. The workflow run fails. For PRs, branch protection (operator action — documented for Phase 4) blocks merge on failed required-status checks. |
| T-03-03 | Tampering | A malicious release of `gitleaks-action` is published under the same tag and silently runs in CI | mitigate | SHA pinning (RESEARCH.md line 540) — the workflow references the exact commit SHA, not the moving tag. The action would have to be force-pushed to that SHA (impossible on GitHub) to compromise. |
| T-03-04 | Denial of Service | gitleaks false-positives on a legitimate non-secret string blocks development | accept | `.gitleaks.toml` `[allowlist]` carve-out exists for documentation paths. Future false-positives can be added there with a targeted regex. Net: occasional friction is preferable to leaked secrets. |
| T-03-05 | Information Disclosure | The pre-commit `no-changeme` hook regexes are run via `bash -c` with command interpolation | accept | The command is a constant string; no user input is interpolated. `git grep` is invoked safely. The exclusion list uses `git grep`'s pathspec syntax (`:!`), not shell glob, so it's safe across all shells. |
| T-03-06 | Tampering | A contributor edits `.gitleaks.toml` to allow a broader pattern, masking a real leak | accept (process control) | Code review (security-reviewer agent per agents.md) catches `.gitleaks.toml` changes. Phase 4 may add a check that `.gitleaks.toml` changes require explicit review labels. Out of scope here. |
| T-03-07 | Information Disclosure | `GITHUB_TOKEN` exposed to the action could be exfiltrated by a compromised action | mitigate | Workflow declares `permissions: contents: read` — least-privilege. The token can read the repo but cannot write to releases, packages, or other repos. SHA-pinning (T-03-03) is the upstream defense. |
| T-03-08 | Information Disclosure | gitleaks scans the entire git history (`fetch-depth: 0`), which may surface PRE-EXISTING leaked secrets that are already public | accept (intentional) | If pre-existing leaks exist, the workflow will fail on the FIRST run and surface them — exactly the desired behavior. Operator must then rotate those secrets (out of repo) and either purge from history or accept the workflow failing pending the rotation. RESEARCH.md and prior context suggest no known historical leaks; if discovered, treat as Phase 1 gap-closure. |
</threat_model>
