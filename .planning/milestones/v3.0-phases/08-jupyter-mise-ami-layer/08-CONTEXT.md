# Phase 8: Jupyter + mise AMI Layer - Context

**Gathered:** 2026-06-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Bake two additions into the Amazon Linux 2023 AMI via the Ansible playbook:
1. **JupyterLab** running as a password-protected systemd service (password sourced
   per-build from SSM, same mechanism as code-server / noVNC).
2. The **mise** version-manager binary, with shell activation but no managed tools.

In scope: the Ansible roles, systemd unit, secrets generation/publish for Jupyter,
boot-time password injection, and mise install/activation. The security-group ingress
rule and `./run` operator-surface wiring are **Phase 9** — not this phase.
</domain>

<decisions>
## Implementation Decisions

### Jupyter flavor + kernels
- **D-01:** Ship **JupyterLab** (not classic Notebook).
- **D-02:** **Python kernel only.** Do NOT register Go/Rust/Java/Node Jupyter kernels — multi-language kernels are out of scope (would be their own phase). Other languages stay reachable via code-server / terminal.

### Python environment backing the kernel
- **D-03:** Run the Jupyter server + kernel from a **dedicated virtualenv** (e.g. `/opt/jupyter`), isolated from the system `python` role's interpreter. Jupyter's dependency tree must not pollute system Python. Users `pip install` into this venv for notebook libraries. (Planner picks the exact path + how the venv's `ipykernel` is registered.)

### TLS / bind posture
- **D-04:** Mirror code-server: bind **`0.0.0.0:8888` with a self-signed cert (HTTPS)**. The Jupyter URL is `https://<host>:8888`. Same self-signed cert warning as `:8080` today is acceptable. No plain HTTP.
- **D-05:** Password auth is mandatory (JUP-04). Jupyter consumes a **hashed** password, but the cleartext is generated by the `secrets` role and stored in SSM SecureString; the boot oneshot fetches cleartext and must hash it into Jupyter's config at boot (HOW = planner/research — JupyterLab uses an argon2/pbkdf2 password hash, not cleartext, in `jupyter_server_config`).

### mise activation
- **D-06:** Activate mise **system-wide via `/etc/profile.d`** (bash), so any login/interactive shell gets it — not only `ec2-user`'s `~/.bashrc`.
- **D-07:** **Zero tools pre-installed** and **no committed `.mise.toml`** (MISE-03). Install the binary + activation hook only; existing per-language Ansible layers (python/golang/rust/java + node) are left untouched.

### Claude's Discretion
- Exact venv path, mise install method (official installer vs package), Jupyter/JupyterLab version pin, and where the self-signed cert comes from (reuse code-server's cert vs generate a Jupyter one) are left to research/planner — but version pinning MUST follow the repo's reproducibility invariants (pin explicit versions, no floating `latest`).
- Notebook working/root directory (e.g. `/home/ec2-user`) — planner's choice; default to ec2-user's home unless a better convention exists.
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`secrets` role** generates + publishes code-server and VNC passwords to SSM SecureString under `/devbox/{{ devbox_user }}/*`. Jupyter password slots in identically (generate.yml + publish.yml + defaults param).
- **Boot oneshot** (`devbox-secrets-bootstrap.sh.j2`) runs at first boot via IMDSv2 + instance profile, fetches each SecureString, writes per-service config, marks `/var/lib/devbox/secrets-applied`, then restarts `code-server.service vncserver.service novnc.service`. Extend: fetch `jupyter-password`, hash it, write Jupyter config, add `jupyter.service` to the restart loop.
- **`vscode` role** is the template for a browser-service role: download/install → write config → install+enable systemd unit. code-server binds `0.0.0.0:8080`, `auth: password`, `cert: true` (self-signed). Jupyter mirrors this on `:8888`.

### Established Patterns
- Per-service password = SSM SecureString fetched at boot (never baked into the image; never in git). Jupyter must follow — cleartext stays out of the AMI and git.
- IAM policy scopes the instance to `/devbox/<user>/*`, so `jupyter-password` under that prefix is already covered by the existing instance-profile policy (verify, but no new IAM expected in Phase 8).
- Reproducibility: explicit version pins, no floating `latest` (CI grep-gates enforce for Packer/Ansible).

### Integration Points
- New `jupyter` role + `mise` role added to `ansible/playbook.yml` (jupyter before `hardening`; mise near language roles).
- `secrets` role extended (generate/publish/defaults + bootstrap template).
- Phase 9 consumes this: the SG rule for `:8888` and `./run` UX depend on the SSM `jupyter-password` path and the running service existing.
</code_context>
